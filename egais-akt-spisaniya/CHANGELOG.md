# Изменения

## 0.1.35
- Кейс 2, режим «только количество»: вместо подсказки «сходите в документ остатков» в плане появляется строка «Запросить марки по справке». Она ставит справку в ту же очередь, что и кейс 4, — отчёт «Остатки в регистре №3» создаёт обработка.
- Строка не отмечается автоматически: запрос уходит только по решению пользователя и при включённом «Разрешить отправку запросов».
- Если справка уже в очереди, выводится прежняя информационная строка со ссылкой на вкладку «Очередь» — повторных запросов нет.

## 0.1.34
- Падение после применения плана: `XMLСтрока(ТипЗнч(Ссылка))` в `ОповеститьОбИзмененииСсылки` — «Ошибка преобразования данных XML». XMLСтрока принимает значение, а не тип; изменения при этом уже были записаны, поэтому выглядело как сбой. Теперь оповещение идёт через `ОповеститьОбИзменении`.
- Контроль количества больше не ругается, когда файл инвентаризации не загружен: раньше отсканированные считались нулём и к списанию выходил весь баланс ЕГАИС. Теперь выводится подсказка загрузить файл на вкладке «Инвентаризация».

## 0.1.33
- «Сформировать план» после «Диагностика»: ошибка «Преобразование к типу Булево» в `ОписаниеТаблицыМарокОтчета()` — флаг `КэшОписаниеОтчетаПостроен` (модульная переменная) мог остаться `Неопределено` при новом экземпляре обработки; проверка через `БулевоИстина()`, инициализация в `ПодготовитьКэшиПланаБезПеречитки()`.

## 0.1.32
- «Диагностика» / план: ошибка «Преобразование к типу Булево» при «кривых» значениях в колонках (старый .epf, данные из хранилища) — безопасное чтение `БулевоИстина()`, поиск в `ИсправленныеСправки` через `НайтиСтроки`.

## 0.1.31
- Ускорена пересборка плана сразу после «Диагностика»: без повторного `ОбновитьПроблемныеПоДанным1С`, без перезаполнения сверки ЕГАИС и без сброса кэша остатков.
- «Диагностика» по-прежнему делает диагностику и план за один проход — отдельное «Сформировать план» нужно только после изменений в 1С или для пересборки строк.

## 0.1.30
- «Сформировать план»: исправлена ошибка «Преобразование к типу Булево» — флаг `ДиагностикаСвежая` инициализируется при открытии, на сервер передаётся через `НужноОбновитьДанные1СПередПланом()`.

## 0.1.29
- Фильтр плана не требует реквизита `ФильтрТипаДействияПлана` в метаданных .epf (хранится в модуле объекта + переменная формы).

## 0.1.28
- Исправлено открытие формы: имя базы берётся из строки соединения (`Ref` / `File`), а не через несуществующее свойство у строки.

## 0.1.27
- Фильтр плана: реквизит **объекта** `ФильтрТипаДействияПлана` (не отдельный реквизит формы) — иначе модуль формы не компилируется.
- При автоматическом запросе отчёта «Остатки в регистре №3» заполняются **алкогольная продукция (алкокод)** и **справка 2** (шапка и, при необходимости, табличная часть `ОтчетЕГАИС`), как при ручном создании в Рознице.
- Алкопродукция подбирается: справка 2 → строки акта → остатки ЕГАИС → марки 1С.
- Документ проводится, если конфигурация позволяет; далее вызывается «Запросить отчёт» (очередь УТМ). Обмен с ЕГАИС пользователь выполняет отдельно.
- Экспорт: `АлкопродукцияПоСправке2()`, `СоздатьОтчетОстаткиРегистр3ПоСправке()` (без отправки в УТМ).

## 0.1.26
- Очередь запросов и инвентаризация хранятся с ключом **имя базы + организация ЕГАИС акта** — параллельный запуск на разных точках (разные базы) без пересечения данных.
- Автоперенос данных со старого ключа `ПомощникАктаЕГАИС`.
- При смене акта перечитываются очередь и инвентаризация; на форме — заголовок с именем базы и версией, опционально `НадписьКонтекстТочки`.
- Экспорт: `КонтекстТочки()`, `ПредставлениеКонтекстаТочки()`, `ПерезагрузитьСохраненноеСостояние()`.
- Инструкция: `docs/08_parallel_retail_stores.md`.

## 0.1.25
- У одной справки может быть несколько проблем (например, номенклатура и статусы). В «Кейс» по-прежнему главная проблема для подсветки, но план строится по **всем** активным кейсам — исправление первой не блокируется второй.
- В описании диагностики добавлено «Также требует исправления: …».

## 0.1.24
- На вкладке «План»: фильтр по типу действия (например, только «Запрос марок»), сводка по отфильтрованным строкам.
- «Отметить все» и «Снять все» работают только по текущему фильтру.
- Команда «Следующий тип» переключает фильтр по порядку обработки (запрос марок → номенклатура → …).

## 0.1.23
- «Диагностика» сразу формирует план (отдельное нажатие не нужно). Кнопка «Сформировать план» остаётся для пересборки плана с повторной сверкой 1С.
- После «Применить подтверждённые» открытые формы акта и перепроведённых ТТН обновляются через оповещение — закрывать документ не нужно.
- После применения и при новых марках из очереди снова выполняются диагностика и план.

## 0.1.22
- После «Диагностика» → «Сформировать план» обработка не повторяет полный запрос диагностики и кейсы 1–2: форма передаёт флаг «данные свежие». Если между шагами что-то меняли в 1С — снова нажмите «Диагностика» или закройте и откройте план с обновлением (повторный «Сформировать план» без свежей диагностики перечитает базу).
- Один запрос марок 1С на акт, один запрос «к списанию» по всем готовым справкам, кэш остатков ЕГАИС с множеством кодов, кэш описания отчёта регистра №3.
- `ВыполнитьДиагностикуИСформироватьПлан()` — оба шага в одном серверном вызове (удобно из своих сценариев).

## 0.1.21
- Ускорение без изменения логики. Проверка состояния марки искала код линейным перебором массива остатков — на справке в тысячи марок это давало квадрат; теперь поиск по множеству.
- Проверка «такая строка уже в плане» просматривала весь план для каждой марки — построен индекс.
- Поиск строк сверки по справке перебирал всю таблицу на каждую справку — построен индекс по справкам.
- Структура адаптера, подготовленные тексты запросов, значения статусов и матрица статусов теперь собираются один раз за вызов, а не на каждое обращение (раньше это были десятки проходов СтрЗаменить по тексту запроса и обращения к метаданным на каждую марку).
- Кэши сбрасываются перед диагностикой, поэтому правки адаптера и изменения в базе подхватываются как раньше.

## 0.1.20
- Колонка сверки «К списанию» заполняется, только если она есть в сборке обработки. Без этой проверки в старой сборке заполнение сверки падало бы с «Поле объекта не обнаружено», как это уже было с «Кандидат по количеству».

## 0.1.19
- План больше не обращается к колонке «КандидатПоКоличеству»: в обработке её нет, из-за этого было «Поле объекта не обнаружено». Кандидат помечается текстом подсказки.

## 0.1.18
- Кейс 1. На этой базе у номенклатуры нет вида продукции, поэтому «водка вместо вина» не считалась ошибкой. Теперь неверной считается марка, у которой номенклатура не совпадает с единственной номенклатурой строки ТТН или с единственным соответствием.
- «Провести и закрыть» для подтверждённой ТТН и подстановка единственной номенклатуры из той же ТТН отмечаются в плане сами. При проведении номенклатура строки переносится на марки справки: и пустые, и с другой номенклатурой.
- Если в однозначном соответствии другая номенклатура, чем в строке ТТН, строка замены тоже отмечается сама.
- Крепость ищется на карточке номенклатуры по имени и синониму. Если реквизита нет, в план пишется одна строка: сравнить крепость вина вручную.

## 0.1.17

- Расхождение видно на вкладке «Сверка» по каждой марке: статус 1С и состояние ЕГАИС. Пока обработка открыта, раз в минуту проверка повторяется. Строка правки в плане отмечается сама, статус в 1С меняется по «Применить подтвержденные».
- «Списано чеком» и «Списано актом» считаются одним статусом — «Реализована». «В резерве» и «на остатках» правятся по ЕГАИС: в обороте — «В наличии», в архиве — «Реализована».

## 0.1.16

- Если номенклатур несколько, «Выбрать номенклатуру» на плане или на сверке показывает только номенклатуры с марок этой алкопродукции и сразу пишет соответствие. Код в справочнике искать не нужно. Новую номенклатуру обработка не создаёт.

## 0.1.15

- Над очередью видно, сколько справок ещё в дозапросе, сколько уже получено и сколько без ответа.

## 0.1.14

- Перед планом диагностика ещё раз читает 1С. Если проблема уже закрыта в базе, справка уходит из проблемных и в план не попадает.
- Однозначная номенклатура из поступления отмечается в плане сама. Найденные марки другой справки показываются в сверке; перепривязка отмечается, только если включён её флажок.

## 0.1.13
- Проверка «реализована, но чека нет» не работала: в табличной части чека ссылка на карточку марки, а `МаркаКод` — строка штрихкода, соединение по разным типам не давало совпадений. Теперь чеки соединяются по карточке, код берётся из регистра марок. Это же чинит подбор кандидатов по количеству: раньше в кандидаты попали бы все «реализованные», включая честно проданные.
- Заполнение акта клало в табличную часть марок строку штрихкода вместо ссылки на карточку (для марок-регистра) — запись акта падала бы по типу. Значение берётся через ключевое измерение.
- Отборы по операции и статусу документа остатков применяются и во втором запросе количеств, а не только при поиске последнего документа.
- «Проверить адаптер» требует `МаркаИзмерение`, если марки лежат в регистре сведений.

## 0.1.12
- Марки в этой базе — регистр сведений: запись статуса, номенклатуры и перепривязка шли по полю `МаркаКод`, а оно задано путём «АкцизнаяМарка.ЗначениеШтрихкода» — отбор набора записей по такому пути невозможен. Добавлено ключевое измерение `МаркаИзмерение` (ссылка на карточку марки), по нему теперь адресуются все изменения.
- Номенклатура марки лежит на карточке (`АкцизнаяМарка.Номенклатура`), а не в регистре: кейс 3 пишет её в объект карточки, а не в набор записей.
- Перепривязка марки к другой справке для регистра реализована: запись пересоздаётся, так как справка 2 — измерение.

## 0.1.11
- Сверка кейса 2 работает и без кодов марок: когда в остатках регистра №1 только количество, подбираются кандидаты на недостачу («в резерве» и «реализована» без проведённого чека, не двигавшиеся после даты остатков).
- Если кандидатов ровно столько, сколько не хватает, подсказка говорит об этом прямо; строки плана не отмечаются — марки проверяются на check1 и подтверждаются вручную.
- В сверке новые колонки: «К списанию» (марка уйдёт в акт) и «Кандидат по количеству».

## 0.1.10
- Кейс 5: марки из файла инвентаризации не попадают в акт списания. Частичное списание больше не считается ошибкой («в наличии 10, в акте 7»).
- Коды марок нормализуются (пробелы, GS1) при сравнении файла и 1С. Список инвентаризации сохраняется между сеансами.
- Проверка акта при заполнении строки смотрит только эту справку, а не валит остальные.

## 0.1.9

- В план не ставим запрос, если остатков регистра №1 нет или по справке в них 0 (после обнуления точки запрос ничего не даст).
- Очередь больше не шлёт N запросов: одна отправка, дальше ждём появления марок в 1С. Повтор всего документа по таймауту отключён.

- Запись в регистр соответствий учитывает периодичность (поле «Период») и необязательные поля формы «Создать»: идентификатор упаковки, характеристика, упаковка. Справку 2 по-прежнему не заполняем.

## 0.1.7

- Кейс 2 работает в двух режимах, потому что в остатках регистра №1 кодов марок нет: по количествам (сколько ЕГАИС числит по справке — отсюда «сколько списать») и по кодам, когда марки по справке 2 получены. Новое значение `ДанныеЕГАИС` — «ТолькоКоличество», новая колонка результатов `ЕГАИСКоличество`.

## 0.1.5
- Кейс 1 по ответам заказчика от 06.10: ТТН ищется по справке 2, а не по основанию марки (основание меняется на чек или акт списания, такие марки раньше выпадали из диагностики).
- Диагностика кейса 1 проверяет номенклатуру самой марки: новая колонка «БезНоменклатуры», «НеверныхНоменклатур» считается по расхождению вида и объёма марки с её алкопродукцией.
- Проведение разрешено только для ТТН в статусе «Подтверждена»: по ответу заказчика только у неё перепроведение ничего не отправляет в ЕГАИС. Неподтверждённые ТТН уходят в план строкой «Информация». Флажок «Разрешить проведение ТТН» включён по умолчанию.
- Одно проведение на документ: действия записывают ТТН без смены проведения, проведение выполняется один раз в конце применения плана. Если провести не удалось, строки плана по этой ТТН помечаются как невыполненные.
- Документы, которые не были проведены, больше не проводятся при записи.
- Диагностика останавливается с понятной ошибкой, если в перечислении нет статуса «В наличии» (раньше все справки молча помечались проблемными).
- В плане показываются код и артикул подобранной номенклатуры — как в ручном процессе, где сотрудник копирует код из поступления.
- Способ связи ТТН с основанием переключён на «РеквизитТТН» (в форме ТТН есть «Документ-основание»); имя реквизита и сам механизм ещё уточняются у заказчика.
